The server that never sleeps

The decision

Two servers, not one

The temptation is to put development on the VPS you're already paying for. That VPS serves six domains and hosts a CI runner: four vCPUs shared between production, continuous integration and an agent compiling Rust. A session that runs wild stops being a failed experiment and becomes a website that's down.

The second temptation is to put Claude in a container. It sounds like isolation, but it isn't: for it to use docker compose and testcontainers you have to mount the host's Docker socket into it, and that's the same as giving it root on the machine. The container stops isolating precisely when you need it to.

What's left is the boring, correct option: a separate machine, a dedicated user with nothing public listening, and restrictive permissions inside Claude.

The mechanism

What keeps a session alive

A Claude Code session is an interactive process: it needs a real terminal and something to keep it on its feet. The chain has three links and each one solves a specific problem.

systemd --user supervises and restarts. tmux provides the pseudo-terminal Claude demands and lets you go in and look without disturbing the session. And enable-linger is the piece people forget: without it, systemd kills all of a user's services as soon as their last SSH session closes — that is, right when you disconnect.

A detail that looks minor and isn't: systemd doesn't read your .bashrc or your .profile. The unit's PATH has to be written out in full, with the mise shims first, or the session will start perfectly and find neither node nor go.

And each service needs its own CLAUDE_CONFIG_DIR. With the default directory, every session writes the same .claude.json and the last one to exit wipes out what the others recorded.

Setup

Two phases and three human snags

The script detects the phase from who runs it, and re-running it breaks nothing. The only thing that can't be automated is the three moments when you have to paste a code or give consent.

  1. Install your key before closing the door

    Phase 1 disables password login. If root doesn't have authorized_keys installed beforehand, the server becomes inaccessible forever. Check that you can get in with the key and then harden.

    # from your machine, with the password your provider gave you
ssh-copy-id root@<IP>
ssh root@<IP> 'echo OK'   # it has to work without asking for anything

  2. Phase 1 — the base

    A dev user, root and passwords out, ufw with only port 22, fail2ban, 4 GB of swap, journald capped, Docker with build-cache GC, and enable-linger.

    ssh root@<IP> 'bash -s' < setup.sh

  3. Phase 2 — tools and projects

    mise with node, go, python, rust and uv; Claude Code in user space; the repos cloned into ~/dev; the systemd template and a restrictive permissions config.

    ssh dev@<IP> 'bash -s' < setup.sh

  4. The two authentications

    GitHub and Claude. Both ask you to open a URL and paste a code, so they need a real terminal — launch them from your own terminal, not from an ssh host 'cmd'.

    ssh dev@<IP> -t 'gh auth login'
ssh dev@<IP> -t 'bash -lc "claude auth login"'

  5. Start and trust

    Each project in ~/dev becomes a named session. The first time, each one asks whether you trust its folder: it's a permission to read, edit and execute there, and you're the one who answers it.

    systemctl --user enable --now claude@blog
# the pane's bottom bar should read: /rc active
What broke

Fourteen failures, and why none of them raised an error

All fourteen share an awkward trait: they fail silently. No exceptions, no journal entries, no non-zero exit codes. Just things that don't happen — or that happen wrongly somewhere nobody looks.

non-interactive shell

mise installs node and npm doesn't exist

mise activate installs a prompt hook. In an ssh host 'cmd', in a script or in a systemd unit that hook never runs and the PATH is never updated.

With set -e, the script died without printing anything. The cure is the shims, which are real binaries: ~/.local/share/mise/shims in the PATH.

empty cgroup

Only the first session starts

Four identical services: the first active, the other three inactive (dead). The journal only says "Started" and then nothing.

They were all talking to the same tmux server. See the diagram below: it's the prettiest failure of the four.

blocking wizard

Live sessions that never show up

Claude's first start launches the onboarding — theme, login method, trust — and with nobody to answer, the session never reaches the prompt. Its login step doesn't reuse the credential you already saved.

Authenticate first and set hasCompletedOnboarding in ~/.claude.json. The trust dialog still appears, and it should keep appearing.

no pty

A login that can't receive the code

ssh -t doesn't allocate a pseudo-terminal if the local stdin isn't one either. The OAuth flow prints its URL and sits waiting for a code nobody can type.

Launch it inside tmux, which does provide a pty, and then inject the code with send-keys. To read the whole URL, capture-pane -J: without the -J it comes out chopped by the pane width.

tls

The free certificate only covers one level

DNS resolves, the IPs are Cloudflare's, and every request dies in 40 ms with curl: (35). No logs at the edge or at the origin.

Universal SSL issues for zone.com and *.zone.com, a single level. p8000.dev.zone.com has two and isn't in the certificate. Flattening to p8000-dev.zone.com fixes it for free; covering it properly is paid.

phantom config

The service ignores the config you wrote

You change the hostnames, restart, and everything returns 404 — including what worked before.

The service runs as root and reads /etc/cloudflared/config.yml, not the one in your $HOME. And service install doesn't overwrite that file if it already exists: it keeps the first version forever.

empty path

The session starts without a single tool

Everything looks fine: node -v works over SSH, the services are active, Claude answers. But when you ask it for an npm run dev or a go test, the command doesn't exist.

systemd doesn't read .bashrc or .profile. Without Environment=PATH, the unit starts with the system's minimal PATH — and starts anyway, because ExecStart invokes claude by absolute path. The failure doesn't show until Claude tries to use something.

shared config

The sessions overwrite each other's configuration

You restart the services and several go back to the trust dialog you had already accepted. In ~/.claude.json only one keeps the flag.

They all write the same file: each process loads it at startup and rewrites it whole on exit. The .claude.json.lock makes the write atomic, not the latest one. The cure is a CLAUDE_CONFIG_DIR per session. Sharing the credentials by symlink doesn't work, and it took us two days to find out: see the next failure.

phantom socket

The Resume button never appeared

Pausing a session worked —systemd stopped it, the memory was freed— but the menu kept offering Pause. The resume button didn't show up even once.

The check was an exists() on /tmp/tmux-1000/claude-<ses>, and tmux leaves the socket behind when the server dies: there was one three days old. The file being there says nothing; what tells them apart is whether anyone answers it. A connect() to the unix socket gives ECONNREFUSED instantly and costs microseconds — 12 ms for seven sessions.

old process in memory

A newly added button that does nothing

You install the new version, tap the button you just added and the spinner goes out without anything happening. No error, no journal line. It happened three times.

install leaves the new file in place, but the process keeps the old one loaded: for it that callback_data doesn't exist and it falls into the else, which answers Telegram and does nothing — indistinguishable from a breakdown. Now the bot compares its own mtime with the one it loaded and exits so systemd relaunches it, and an unknown button says so instead of swallowing it.

false alarm

Seven alerts for the same port in one afternoon

The watchdog alerts once a day per exposed port. 4173 —a Vite preview— alerted seven times in one afternoon, with the daily limit set and working.

The limit is stored as a mark on disk, and the mark was deleted as soon as the port stopped being seen, "to alert again if it reappears tomorrow". On a development machine it doesn't reappear tomorrow: it reappears three minutes later, as soon as you restart the server. The marks are no longer deleted for that; they're collected after a week. An alarm that cries wolf ends up ignored, which is worse than not having one.

last-use filter

A disk sweep that reclaimed 0 B

docker builder prune --filter until=336h over 8.3 GB of build cache with three-week-old entries. It reclaimed zero bytes, without failing or warning.

BuildKit's until filter looks at last use, not when it was created: a layer from three weeks ago that a build touched yesterday is "new". And the cache shared with a live image isn't released even if it hasn't been touched for a month. With a ceiling it does work, because BuildKit evicts in order of last use until it's below it — it keeps the working set and doesn't depend on guessing an age.

two different timeouts

A command that took 47 seconds

You type /status from your phone and the reply takes almost a minute. The bot isn't busy: it's waiting.

The timeout of getUpdates and the socket's are two different things, and confusing them costs you the difference. Telegram holds the response for as many seconds as you ask; if the connection dies silently —565 times in seven days, counted in the journal— the client doesn't notice until its timeout fires, and meanwhile your command sits on the server with nobody picking it up. Now the socket's timeout sits just above the long-poll, with TCP keepalive probes.

credential race

Two idle sessions lose their login at the same time

After 21 hours, two of the three lose Remote Control. Their .credentials.json have an accessToken and refreshToken of zero length, written one second apart. The processes are still alive, so Restart=on-failure never fires.

The refresh token is single-use. When the access token expires, each session tries to refresh with its copy of the same token; one wins and the others get a rejection, in response to which Claude Code deletes the stored credentials. And they're copies because the symlink from the previous failure doesn't survive: the atomic write is temp + rename, and a rename replaces the link with a file. The sharing lasted until the first refresh.

Re-authentication

An interactive login with nobody in front of it

When the credentials get emptied, the cure is /login. Restarting the service is useless: the session comes back up and fails for the same reason, losing the conversation along the way. And /login is interactive — it asks you to open a URL in a browser and paste a code back.

But of that whole procedure, the only part that needs a human is authorizing in the browser. Reading the URL from the pane and typing the code are mechanical, and tmux exposes them: capture-pane to read, send-keys to write. What's missing in between is a channel to your pocket.

Once the code is in, there's nothing else to do: the documentation is explicit that Remote Control reconnects on its own after the login, and the local conversation is never interrupted.

Operations

Day to day

The VPS and your laptop are independent machines, each with its own session history. Git is the meeting point: commit before switching places, pull when you arrive.

# adding a new project
cd ~/dev && gh repo clone <owner>/<repo>
systemctl --user enable --now claude@<repo>

# go in and look without disturbing (Ctrl-b d to leave)
ssh dev@<IP> -t tmux -L claude-<repo> attach -t claude-<repo>

# secrets: never through git
scp .secrets.json dev@<IP>:~/dev/<repo>/
ssh dev@<IP> 'chmod 600 ~/dev/<repo>/.secrets.json'

From your phone

Operating without opening a terminal

Seven sessions at 0.5–1 GB don't fit comfortably in 8 GB of RAM, so each one carries its own ⏸ Pause. It's stop and not disable --now, and that distinction is the whole design: the instance stays enabled, so the repo, the config dir and the conversation stay where they were, and since the unit starts with --continue, ▶️ Resume picks it up at the same point. The message says how much memory was freed, which is the reason for tapping it. After a machine reboot they all come back; if what you want is for it not to come back, that's Close.

The watchdog alerts once a day for each port listening outside loopback. Before, muting one meant remembering a file's path and going in over SSH — which doesn't scale on a machine where servers get started by hand, and ended in seven alerts for the same port in one afternoon. Now the alert carries the button that mutes it, and the loop closes without leaving Telegram.

/ports shows the full inventory in three groups, because they're three situations and only one asks you to do something: what will alert today with its 🔇 next to it, what's muted by hand with the 🔊, and what only listens on 127.0.0.1 —eleven of this machine's thirteen ports— which doesn't alert and can't, and so carries no button. Behind each port, who serves it and how long it's been up.

Both ss and docker ps are needed even though it looks redundant: with the userland proxy a published port does show up in ss, but as docker-proxy running as root, i.e. a socket with no owner; and without the proxy the publication is pure DNAT and there's nothing to see in ss. Where someone else's process can't be seen, the owner is left out rather than made up.

Disk

It fills up where you don't expect

docker system df said 9.8 GB "reclaimable" and the temptation was a daily system prune -a. Looking at the detail, no: almost all of that is tagged images the next build would download again.

WhatReclaimableSwept by the timer
Dangling images (<none>)0 GByes
Build cache3.8 GByes, with a 4 GB ceiling
Containers stopped > 1 week—yes
Unused tagged images6.1 GBno — it sends you the list
Unused volumes0.4 GBnever

The last two rows are the design decision. An inactive volume is what's left between a compose down and the next up — someone's database; --volumes doesn't appear in the script. And a machine can't tell "experiment from two weeks ago" from "tomorrow's base", so tagged images aren't automated: when the disk goes over 75 %, the bot sends the list sorted by size and you choose.

The cache ceiling bites on the cache's own share. The part shared with a live image isn't released until the image is deleted, so the total stays above the cap and that isn't a failure: measured here, 4.10 GB of its own against a 4 GB cap, and another 3 GB that travel with their images.

Previews

Seeing the work from your phone

An agent that works while you're away is of little use if you can't look at what it's done. A Cloudflare tunnel publishes the development servers over HTTPS without opening a single inbound port: cloudflared connects outwards, exactly like the Claude sessions. The firewall still has a single open port, 22.

The mapping is per port, not per project: p3000-dev, p5173-dev, p8080-dev… So anything you start already has a URL, without touching the tunnel config or waiting for DNS propagation.

What Claude can't do

The limits are part of the setup

With one exception worth saying out loud: those URLs are public while the server is up, and the only barrier is that nobody guesses the subdomain. Cloudflare Access in front, with your email, isn't optional.

The permissions config isn't bureaucracy: it's what makes it defensible to leave an agent running on a machine with access to your repos and your GitHub token, which on a headless server is stored in plain text.

Denied: git push, sudo, systemctl, ufw, and reading .env, .secrets.json, *.pem, *.key and id_rsa. Publishing and touching the system are your decisions; secrets can't end up in a commit or a log because Claude never gets to see them.

The workspace trust dialog falls into the same category. It appears once per project and it's tempting to automate it — it's exactly the permission you shouldn't give away for convenience.

Script, runbook and full diagnostics in the pocket-agents repository. The IPs are parameterized: nothing about real infrastructure is written into the repo.
